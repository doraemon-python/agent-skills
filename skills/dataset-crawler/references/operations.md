# 運用ガイド

## 定期実行

取得（`crawl`）と抽出を分けて考える。

| 工程 | AI が必要か | 回し方 |
| --- | --- | --- |
| 取得 `crawl` | 不要 | cron / launchd / タスクスケジューラ |
| 機械的な抽出 `auto-extract` | 不要（extractor がある source のみ） | 取得の後に続けて実行 |
| 判断を伴う抽出・レビュー | 必要 | エージェントのセッションで、またはエージェントのスケジュール機能で |

### cron で取得だけ回す

```bash
# 毎時 0 分に最大 200 リクエスト・50 分まで取得する（パスは絶対パスで書く）
0 * * * * cd /path/to/dataset && /path/to/uv run /path/to/skills/dataset-crawler/scripts/crawler.py -d . crawl --max-requests 200 --max-minutes 50 >> logs/cron.log 2>&1
```

- 終了コード 0: 予定どおり終了（上限到達・キューが空・次の再訪問まで待ち）。3: レートリミットや連続エラーで中断。130: Ctrl-C。どれも次回の実行で続きから再開する
- `crawl` を同時に 2 つ走らせない（`--max-minutes` を実行間隔より短くする）。ホストごとの「1 本ずつ」は 1 プロセスの中でしか守られないため、同じホストへの間隔が崩れる。
  速くしたいときはプロセスを増やさず、`crawl.concurrency`（同時に取得するホスト数）を上げる
- 抽出待ちがたまったら、エージェントのセッションで「続きを抽出して」と頼む

### エージェントに定期的に任せる

Claude Code なら `/loop`（セッション中に繰り返す）や `/schedule`（クラウドで定期実行）、
ヘッドレス実行（`claude -p "dataset-crawler で <dir> の続きを進めて、終わったら status を報告"`）を cron から呼ぶ方法がある。
他のエージェントでも、「`status` を見て、取得 → 抽出 → 報告」を 1 回分の指示として渡せばよい。
無人で回すときは、レビュー待ち（`confidence: low`）がたまる前提で、人が `review` する機会を作る。

## 並行取得のしくみ

- `crawl` は非同期で動き、取得中でも待機中でもないホストの URL を、`concurrency` 本まで同時に取得する。
  キューは優先度順だが、あるホストが待ち時間中なら、その間に他のホストの URL を先に取得する
- 同じホストへは常に 1 本ずつ。応答を受けてから `delay_sec`（または robots.txt の Crawl-delay）経つまで次のリクエストを出さない。
  ホストの単位は「ホスト名 + ポート」。`www.example.com` と `img.example.com` は別ホストとして並行に取得される
- `store` で file / image 列の URL を渡したときも、書き込みの前に同じ規則でまとめて並行ダウンロードする
- HTML の解析・`raw/` への保存はスレッドで行い、進捗 DB の更新はメインスレッドだけで行う

## レートリミットと中断・再開

- 進捗は 1 ページごとに `state/crawl.sqlite` にコミットされる。強制終了・PC のスリープでも、次の `crawl` で続きから再開する
- Ctrl-C を 1 回押すと、新しい取得をやめ、取得中のリクエストが終わってから記録して終了する。2 回押すと取得中のものも打ち切る（その URL はキューに残る）
- HTTP 429 / 503 を受けると、`Retry-After` の秒数（無ければ `delay_sec` の 10 倍から倍々、上限 `max_backoff_sec`）だけそのホストを待たせる。`Retry-After` は上限より長くても短縮しない。他のホストの取得は続く。
  URL はキューに残り、失敗回数にも数えない
- 取得できる URL が無くなり、次に取得できるまでの待ち時間が `--max-wait`（既定 60 秒）より長ければ実行を終了する
- 同じホストで `max_consecutive_errors` 回連続で失敗（403・5xx・通信エラー）すると、ブロックの可能性があるので、その実行ではそのホストを取得しない（他のホストは続行し、終了コードは 3）。
  時間をおいても続くなら、`delay_sec` を伸ばす・取得範囲を絞る・API がないか確かめる。UA の偽装やプロキシでの回避はしない
- 5xx・通信エラーは 2, 4, 8 分…と間隔を空けて `max_retries` 回まで再試行し、それでもだめなら `failed`。
  原因が解消したら `add-urls --requeue <URL>` で戻す

## よくある調整

| 症状 | 対処 |
| --- | --- |
| 関係ないページばかりキューに入る | `allow` を狭める・`deny` を足す。既に入った URL は次回の crawl で `blocked` になる |
| 同じページが別 URL で何度も取られる | 並び順・セッション ID などのパラメータを `strip_params` に足す |
| 一覧の 2 ページ目以降に進まない | 次へのリンクが JavaScript で生成されている。`pages` の URL を `add-urls` で入れるか、API を探す。`render_js` は最後の手段 |
| 抽出待ちがどんどん増える | 抽出の方が遅い。`crawl --max-requests` を減らすか、extractor を作る |
| 複数サイトを回しているのに遅い | `crawl.concurrency` を対象ホスト数まで上げる。1 サイトだけなら速くならない（同じホストは 1 本ずつのため） |
| 詳細ページを再取得しても抽出されない | 内容が変わっていない（`unchanged`）。基準を変えたなら `reextract` |
| 判断基準を変えたい | `conventions` を直して `reextract --source <id>`（スキーマ変更ではない） |
| 列を足したい・型を変えたい | SKILL.md の「スキーマ変更」の手順（承認 → schema_version を上げる → `migrate`） |
| 一覧ページの値も抽出したい | その `pages` を `extract: true` にし、`add-urls --requeue` で取り直す（それまでの一覧は抽出対象外として保存されているため） |

## 容量とバックアップ

- `raw/` は内容ハッシュで重複を除いた gzip。1 ページ 10〜50KB 程度なので、10 万ページで数 GB を目安にする
- 古い取得結果を消して容量を空けたくなっても、`raw/` は消さない（スキーマ変更時に作り直せなくなる）。必要なら外部ストレージに移す
- バックアップ対象: データセットのディレクトリ全体。最低でも `dataset.yaml`・`state/`・`raw/`・`logs/`

## 法令・マナー

- 利用規約でクロールやデータの二次利用が禁止されていないか確認する。禁止されていれば取得を始めず、そのことをユーザーに伝える
- robots.txt に従い、`delay_sec` は 3 秒以上を基本にする。深夜帯に回すなど相手の負荷も考える
- 収集したデータの再配布・公開は、著作権・規約・個人情報保護の観点で別途確認が必要なことをユーザーに伝える
