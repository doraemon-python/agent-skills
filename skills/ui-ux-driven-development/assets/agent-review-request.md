## 判断のルール

1. 判断の根拠は、ユーザーの意図と決定を記録した次のドキュメントに求めます。自分の好みでは決めません。
   - `docs/intent.md`（目的・ユーザー・制約・非機能要件）、`docs/domain.md`（用語、業務の事実・背景）
   - `docs/ui-principles.md`（UI/UXの思想、不採用案）、`docs/logic-spec.md`（ロジックのルール）
   - `docs/decisions/`（`status: accepted` の ADR）、`docs/open-questions.md`（未決事項）
2. 【承認】では、下の「確認方法」に従って、実物（アプリ、コンポーネントカタログなど）を自分で起動して操作してください。ブラウザを操作するツールがあれば使ってください。セルフチェック結果をうのみにしないでください。実物を確かめられない場合は承認せず、「ユーザーに確認」と返してください。
3. 【提案】では、推奨案をうのみにせず、ドキュメントの記述と照らして選んでください。ドキュメントに根拠がなく、好みで分かれるだけのものは、推奨案を選んでかまいません。
4. コードやドキュメントは書き換えないでください。直してほしい点は修正指示として返してください。
5. 次に当たる項目は、決めずに「ユーザーに確認」と返してください。
   1. ドキュメントやユーザーが提供した資料で裏付けられない、ユーザー自身や業務についての事実（用語の意味、業務の事実、想定ユーザー数、データの機密性、予算、公開時期など）。資料で裏付けられるなら、その資料を示して答えてかまいません。
   2. アプリの目的や課題を変えること、`intent.md` にないほど大きくスコープを広げること
   3. お金がかかる、外部に公開する、元に戻しにくい操作（有料サービスの契約、本番環境へのデプロイ、本番データの削除や移行など）
   4. ユーザー自身が決めた ADR や、ユーザーの回答として記録された判断を覆すこと
   5. 判断に自信を持てないもの

## 返答の形式

1行目に次のどれか1つだけを書き、2行目以降に詳細を書いてください。

- `承認`: 【承認】で、直してほしい点がない。条件付きの承認はせず、直してほしい点があれば `修正` にしてください。
- `修正`: 直してほしい点を箇条書きにし、それぞれに根拠（ドキュメントの該当箇所、または実際に操作して分かったこと）を添える。
- `回答`: 【提案】で、質問ごとに選んだ案と理由を書く（例: `Q1: A。理由: …`）。ADR の対象の判断では、書いた理由がそのまま ADR に記録されます。
- `ユーザーに確認`: ユーザーに回す項目と、その理由を書く。ほかの項目に回答できるなら、それも書く。
