# Step 6. ロジック仕様の決定

UIの作成で得られた知見をもとに、バックエンドのロジック仕様（権限、バリデーション、計算ロジックなど）を決める。ここで書く `logic-spec.md` は永続ドキュメントだが、コードと食い違わないよう、テストを「実行できる仕様」と位置づけ、ドキュメントには「何を」と「なぜ」だけを簡潔に書く。

ロジックのルールとその理由は `logic-spec.md` に書き、ADR にはしない。ルールを実現するための技術的な判断（どの層で認可するか、など）は Step7 で扱う。

`logic-spec.md` に書くのは、このアプリで決めた挙動だけにする。ルールの根拠になる業務の事実（法令、業界の慣習、計算式、業務の流れなど、アプリの外で決まっていること）は `docs/domain.md` に書き、ルールの「根拠」欄からその ID（D-001 など）を参照する。同じ内容を両方に書き写さない。

## 手順

1. `docs/domain.md`（分けている場合は `docs/domain/README.md` の一覧から、関係するファイル）を読む。
2. ルールを洗い出す。次を対象にする。
   1. `logic-spec.md` の「UI由来ルール（未確定）」
   2. データアクセス層の各関数について、誰が実行できるか（権限）
   3. サーバー側のバリデーション
   4. 計算ロジック
   5. 状態の遷移（ステータスなど）
   6. 異常系（存在しない、権限がない、同時編集による競合、上限超過、関連データがある状態での削除）
   7. 外部サービスとの連携
3. 各ルールを「誰が・いつ・何をすると・どうなる（できない場合はどうなる）」の形で、1ルール数行に書く。
4. ルールが業務の事実に基づく場合は、その事実が `domain.md` にあるかを確かめる。あれば「根拠」欄にその ID を書く。なければ、ユーザーの回答か資料で裏付けられるものだけを `domain.md` に追記してから参照する。裏付けがなければ 6 で聞く。
5. 各ルールにID（R-001 など）を振る。対応するテストの欄は Step8 で埋める。
6. **【提案P6】** ドメイン知識に由来して判断できないルールや、複数の妥当な挙動があるルールは、推測せずに選択式で質問する。「この操作をするとUI上ではこう見える」という具体例を添えると判断しやすい。回答を待つ。
7. 回答を反映する。新しく分かった用語や業務の事実は、出典（回答日／資料）を付けて `docs/domain.md` に追記する。このアプリでの挙動は `logic-spec.md` に書き、「UI由来ルール（未確定）」の項目を確定したルールに移す。
8. 「Step6 チェックリスト」を実行する。全項目を満たしたら Step7 へ進む（ここでは承認を求めない。【承認D】でバックエンド設計と一緒に確認してもらう）。

## Step6 チェックリスト

- [ ] データアクセス層のすべての関数について、権限とバリデーションが決まっている
- [ ] 「UI由来ルール（未確定）」のすべての項目が、確定したか「後で決める（理由付き）」になっている
- [ ] 推測で決めたルールがない
- [ ] すべてのルールにIDがあり、自明でないものには「なぜ」が書かれている
- [ ] 異常系の挙動がすべて決まっている
- [ ] 各ルールが数行に収まっている
- [ ] 業務の事実（法令、計算式など）を `logic-spec.md` に書き写しておらず、「根拠」欄で `domain.md` の ID を参照している
- [ ] このStepで新しく分かった用語と業務の事実が、出典付きで `domain.md` に追記されている
