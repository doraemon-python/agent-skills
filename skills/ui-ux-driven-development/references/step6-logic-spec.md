# Step 6. ロジック仕様の決定

UIの作成で得られた知見をもとに、バックエンドのロジック仕様（権限、バリデーション、計算ロジックなど）を決める。ここで書く `logic-spec.md` は永続ドキュメントだが、コードと食い違わないよう、テストを「実行できる仕様」と位置づけ、ドキュメントには「何を」と「なぜ」だけを簡潔に書く。

ロジックのルールとその理由は `logic-spec.md` に書き、ADR にはしない。ルールを実現するための技術的な判断（どの層で認可するか、など）は Step7 で扱う。

## 手順

1. ルールを洗い出す。次を対象にする。
   1. `logic-spec.md` の「UI由来ルール（未確定）」
   2. データアクセス層の各関数について、誰が実行できるか（権限）
   3. サーバー側のバリデーション
   4. 計算ロジック
   5. 状態の遷移（ステータスなど）
   6. 異常系（存在しない、権限がない、同時編集による競合、上限超過、関連データがある状態での削除）
   7. 外部サービスとの連携
2. 各ルールを「誰が・いつ・何をすると・どうなる（できない場合はどうなる）」の形で、1ルール数行に書く。
3. 各ルールにID（R-001 など）を振る。対応するテストの欄は Step8 で埋める。
4. **【提案P6】** ドメイン知識に由来して判断できないルールや、複数の妥当な挙動があるルールは、推測せずに選択式で質問する。「この操作をするとUI上ではこう見える」という具体例を添えると判断しやすい。回答を待つ。
5. 回答を反映し、「UI由来ルール（未確定）」の項目を確定したルールに移す。
6. 「Step6 チェックリスト」を実行する。全項目を満たしたら Step7 へ進む（ここでは承認を求めない。【承認D】でバックエンド設計と一緒に確認してもらう）。

## Step6 チェックリスト

- [ ] データアクセス層のすべての関数について、権限とバリデーションが決まっている
- [ ] 「UI由来ルール（未確定）」のすべての項目が、確定したか「後で決める（理由付き）」になっている
- [ ] 推測で決めたルールがない
- [ ] すべてのルールにIDがあり、自明でないものには「なぜ」が書かれている
- [ ] 異常系の挙動がすべて決まっている
- [ ] 各ルールが数行に収まっている
