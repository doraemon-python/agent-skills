# Step 8. 実装・テスト・結合

承認された設計を実装し、ロジックに誤りがないよう豊富なテストを作り、UIを本物のバックエンドにつなぐ。承認済みの仕様の実装なので、承認は求めず報告だけにする。

実装中に仕様や設計の変更が必要になった場合は、その変更だけを【提案】で確認する。変更が ADR の対象になる場合（Step7 で記録した決定を変える場合を含む）は、`assets/adr-proposal.md` の形式で1つずつ聞き、回答を得てから ADR を書く。既存の ADR を変えるときは、本文を書き換えずに新しい ADR で置き換える。

## 手順

1. `logic-spec.md` のルールIDごとに、先にテストを書く。テスト名にルールIDを含める（例: `R-012: 他人のプロジェクトは削除できない`）。
2. バックエンドを実装する。
3. テストを実行する。正常系に加えて、異常系、境界値、権限のないアクセスを必ず含める。
4. UIを結合する。データアクセス層の実装をモックから本物に差し替える。モック実装は削除せず、コンポーネントカタログとテスト用に残す。
5. 本物のデータで、UIの各状態（読み込み中、エラー、0件）が正しく表示されることを確認する。サーバーのエラーが、UI上で適切なメッセージに変換されることも確認する。
6. 主要なユースケースについて、E2Eテストを書く（E2Eツールを採用していない場合は、手動で確認した手順と結果を `progress.md` に残す）。
7. `logic-spec.md` の各ルールに、対応するテスト名を書き込む。
8. ADR の決定を知らないと「直したくなる」コード（一見不自然な実装など）を見つけたら、ADR 参照コメントを入れる候補として `progress.md` に控える。コメントは【承認E】の依頼で候補を示し、同意を得てから入れる。
9. ADR の `code` が実際のパスとずれていれば、`code` だけを直す。
10. 「Step8 チェックリスト」を実行する。
11. `_tmp/backend-design.md` の内容のうち残すべき判断を移す。ロジックの判断は `logic-spec.md` へ。技術的な判断は Step7 で ADR にしたはずなので、漏れがないかを確かめる。ADR の基準を満たすのにまだ記録していない判断があれば、`assets/adr-proposal.md` の形式で1つずつ【提案】で聞き、回答を得てから記録する。その後 `_tmp/backend-design.md` を削除する。
12. `progress.md` を更新し、完了を簡潔に報告して Step9 へ進む。

## Step8 チェックリスト

- [ ] すべてのルールIDに対応するテストがあり、通っている
- [ ] 権限のないアクセスが拒否されることのテストがある
- [ ] すべてのテスト、型チェック、リンターが通る
- [ ] 本番と同じ構成で、モックが無効になり本物のバックエンドで動作している
- [ ] サーバーのエラーがUI上で適切に表示される
- [ ] 主要なユースケースのE2Eテスト（または手動確認の記録）がある
- [ ] コンポーネントカタログが引き続きモックで動作する
- [ ] `logic-spec.md` のすべてのルールに、対応するテスト名が書かれている
- [ ] 実装が有効な ADR の決定と食い違っていない（変えた場合は、提案で確認して置き換える ADR を書いた）
- [ ] すべての ADR の `code` が、実際に存在するパスを指している
