# 追加開発フロー

機能追加、UIの変更、バグ修正などの追加開発では、変更の規模に応じて開始するStepと承認の回数を変える。小さな変更に初期開発と同じ重さのプロセスを適用すると、運用が形骸化するためである。

## 手順

1. `progress.md` に、追加開発の内容と開始日を記録する。
2. 変更する範囲に関係する ADR を探して読む。`rg -l "code:.*<変更するパス>" docs/decisions/` と、索引 `docs/decisions/README.md` のタイトル・タグで探す。`revisit_if` が満たされていれば、ユーザーに伝える。変更が有効な ADR の決定に反する場合は、黙って反せず、置き換えるかどうかを【提案】で確認する。
3. 変更する範囲に関係するドメイン知識を `docs/domain.md`（分けている場合は `docs/domain/README.md` の一覧から、関係するファイルだけ）で確認する。`docs/domain.md` がない古いプロジェクトでは、`assets/domain.md` から作り、`intent.md` に用語集やドメインのロジックがあればそこへ移す（挙動のルールは `logic-spec.md` へ）。
4. 変更の種類を判断し、下の表から開始Stepと承認ゲートを決める。複数に当てはまる場合は、最も前のStepから始める。
5. 次の条件に当てはまる場合は、表の開始Stepより前に、該当部分だけを行う。
   1. ドメイン知識に不明点がある → Step1 の該当部分（**【提案P1】**）を先に行い、回答を出典付きで `docs/domain.md` に追記する。
   2. 新しいライブラリの導入が適切 → Step2 の該当部分（**【提案P2】**）を行い、導入するライブラリだけを【承認A】の手順で確認してもらう。ADR の基準を満たす場合は、承認依頼に入れず、先に `assets/adr-proposal.md` の形式で1つずつ【提案】で聞き、回答を得たら ADR を書く。
6. 表の開始Stepから、各Stepの手順とチェックリストに従って進める。Step内の手順のうち、変更に関係しない部分は省略してよい。ADR に関する手順は省略しない。
7. 作業中に新しく分かった用語や業務の事実は、出典（回答日／資料）を付けて `docs/domain.md` に追記する。推測で書かず、不明なら【提案】で聞く。追記して分割の目安を超えたら、`SKILL.md` の「ドメイン知識の置き場所」に従って `docs/domain/` に分ける。
8. 完了したら `progress.md` を更新する。

| 変更の種類 | 開始Step | 承認ゲート |
|---|---|---|
| 新しい画面の追加、遷移の変更 | Step3 | B → C → D → E |
| 既存の画面内でのUI変更 | Step4（Step3は省略） | C →（ロジック変更があれば D）→ E |
| UIの変更を伴わないロジックの変更 | Step6 | D → E |
| バグ修正 | 下の「バグ修正の手順」 | 仕様の変更を伴う場合のみ E |

変更が小さい場合（1画面の中で完結し、ロジックの変更が数ルール以内）は、【承認D】を省略して【承認E】に統合してよい。その場合も、Step6 と Step7 のチェックリストは実行する。ADR の対象になる判断は、承認を省略しても、Step7 と同じく1つずつ【提案】で聞いて決める。

## バグ修正の手順

1. 再現手順を確認する。不明な場合は **【提案】** として質問する。
2. バグを再現する、失敗するテストを書く。
3. 原因を次の3つに分類する。
   1. 実装の誤り（仕様は正しい）
   2. 仕様の誤り
   3. 仕様の抜け
4. 実装の誤りの場合は、修正してテストを通し、類似の箇所に同じ誤りがないか確認して、報告する（承認は不要）。
5. 仕様の誤りや抜けの場合は、**【提案】** で正しい挙動を確認し、`logic-spec.md` または `ui-principles.md` を更新してから修正する。原因が業務の事実の誤解や抜けなら、`domain.md` も直す（事実は `domain.md`、挙動は `logic-spec.md`）。修正後、**【承認E】** の手順で、変更した挙動だけを確認してもらう。
6. 原因が ADR の決定そのもの（選んだ技術や設計が要件に合っていない）にある場合は、`references/adr.md` に従って選択肢を【提案】で示し、決まったら古い ADR を置き換える新しい ADR を書いてから修正する。
