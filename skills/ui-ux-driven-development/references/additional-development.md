# 追加開発フロー

機能追加、UIの変更、バグ修正などの追加開発では、変更の規模に応じて開始するStepと承認の回数を変える。小さな変更に初期開発と同じ重さのプロセスを適用すると、運用が形骸化するためである。

## 手順

1. 依頼の作業に入る前に、`progress.md` を読み、終わっていない作業を確認する。
   1. 「未着手の作業」に項目があれば、一覧（内容と記録日）をユーザーに伝える。
   2. 依頼の影響範囲（画面、ファイル、ルールID、ADR）を見積もり、未着手の作業の影響範囲と比べる。同じ画面・ファイル・ルール・ADR に触れる場合や、依頼が未着手の作業の前提を変える場合（未着手の作業が手を入れる画面を削除する、など）は、競合の可能性がある。
   3. 「現在の状態」が作業中・回答待ち・承認待ちのまま終わっていない前のフローがあれば、それも同じように比べる。競合しなくても、中断して今回の依頼を先に進めてよいかを確認する（`progress.md` の「現在の状態」は1つしか持てないため）。中断する場合は、前のフローの残りを「未着手の作業」に移す。
   4. 競合の可能性があれば、どの作業と、なぜぶつかるかを警告し、進め方を【提案】で聞いて回答を待つ。選択肢の例: 未着手の作業を先に（または今回の作業と一緒に）片付ける ／ 今回の依頼を先に進め、終わったら未着手の作業の内容を見直す ／ 未着手の作業を取りやめる（反映先の記述も元に戻す）。
   5. 競合がなければ、伝えるだけで次へ進む。ユーザーが未着手の作業にも着手したいと言えば、今回の作業に含める。
2. `progress.md` に、追加開発の内容と開始日を記録する。今回の作業に含めた未着手の作業も書く。
3. 変更する範囲に関係する ADR を探して読む。`rg -l "code:.*<変更するパス>" docs/decisions/` と、索引 `docs/decisions/README.md` のタイトル・タグで探す。`revisit_if` が満たされていれば、ユーザーに伝える。変更が有効な ADR の決定に反する場合は、黙って反せず、置き換えるかどうかを【提案】で確認する。
4. 変更する範囲に関係するドメイン知識を `docs/domain.md`（分けている場合は `docs/domain/README.md` の一覧から、関係するファイルだけ）で確認する。`docs/domain.md` がない古いプロジェクトでは、`assets/domain.md` から作り、`intent.md` に用語集やドメインのロジックがあればそこへ移す（挙動のルールは `logic-spec.md` へ）。
5. 変更の種類を判断し、下の表から開始Stepと承認ゲートを決める。複数に当てはまる場合は、最も前のStepから始める。
6. 次の条件に当てはまる場合は、表の開始Stepより前に、該当部分だけを行う。
   1. ドメイン知識に不明点がある → Step1 の該当部分（**【提案P1】**）を先に行い、回答を出典付きで `docs/domain.md` に追記する。
   2. 新しいライブラリの導入が適切 → Step2 の該当部分（**【提案P2】**）を行い、導入するライブラリだけを【承認A】の手順で確認してもらう。ADR の基準を満たす場合は、承認依頼に入れず、先に `assets/adr-proposal.md` の形式で1つずつ【提案】で聞き、回答を得たら ADR を書く。
7. 表の開始Stepから、各Stepの手順とチェックリストに従って進める。Step内の手順のうち、変更に関係しない部分は省略してよい。ADR に関する手順は省略しない。
8. 作業中に新しく分かった用語や業務の事実は、出典（回答日／資料）を付けて `docs/domain.md` に追記する。推測で書かず、不明なら【提案】で聞く。追記して分割の目安を超えたら、`SKILL.md` の「ドメイン知識の置き場所」に従って `docs/domain/` に分ける。
9. 作業中に未決事項に回答を得たら、`SKILL.md` の「未決事項と未着手の作業」に従って片付ける。
10. 完了したら `progress.md` を更新する。今回実装した未着手の作業は一覧から消し、反映先の「（未実装）」を外す。そのうえで `SKILL.md` の「フローの終わりに progress.md を片付ける」に従って片付ける。

| 変更の種類 | 開始Step | 承認ゲート |
|---|---|---|
| 新しい画面の追加、遷移の変更 | Step3 | B → C → D → E |
| 既存の画面内でのUI変更 | Step4（Step3は省略） | C →（ロジック変更があれば D）→ E |
| UIの変更を伴わないロジックの変更 | Step6 | D → E |
| バグ修正 | 下の「バグ修正の手順」 | 仕様の変更を伴う場合のみ E |

変更が小さい場合（1画面の中で完結し、ロジックの変更が数ルール以内）は、【承認D】を省略して【承認E】に統合してよい。その場合も、Step6 と Step7 のチェックリストは実行する。ADR の対象になる判断は、承認を省略しても、Step7 と同じく1つずつ【提案】で聞いて決める。

## バグ修正の手順

1. 再現手順を確認する。不明な場合は **【提案】** として質問する。
2. バグを再現する、失敗するテストを書く。
3. 原因を次の3つに分類する。
   1. 実装の誤り（仕様は正しい）
   2. 仕様の誤り
   3. 仕様の抜け
4. 実装の誤りの場合は、修正してテストを通し、類似の箇所に同じ誤りがないか確認して、報告する（承認は不要）。
5. 仕様の誤りや抜けの場合は、**【提案】** で正しい挙動を確認し、`logic-spec.md` または `ui-principles.md` を更新してから修正する。原因が業務の事実の誤解や抜けなら、`domain.md` も直す（事実は `domain.md`、挙動は `logic-spec.md`）。修正後、**【承認E】** の手順で、変更した挙動だけを確認してもらう。
6. 原因が ADR の決定そのもの（選んだ技術や設計が要件に合っていない）にある場合は、`references/adr.md` に従って選択肢を【提案】で示し、決まったら古い ADR を置き換える新しい ADR を書いてから修正する。
7. 修正が終わったら、上の「手順」の10に従って `progress.md` を更新し、片付ける。
