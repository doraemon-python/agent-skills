# Step 7. バックエンドの設計

ロジック仕様とデータアクセス層のインターフェースをもとに、バックエンドを設計する。モックデータの形（画面に表示するための形）とドメインとして正しいデータの形は一致しないことが多いので、データアクセス層のインターフェースは「画面が必要とするものの契約」として扱い、DBスキーマはドメインの概念から別に設計する。セキュリティには特に注意する。

ここでの技術的な判断の多くは ADR の対象になる。ADR の手順と書式は `references/adr.md` に従う。

## 手順

1. `docs/decisions/` の有効な ADR（Step2 で記録したものなど）を読み、設計の前提にする。`revisit_if` が満たされているものがあれば、提案で取り上げる。
2. `open-questions.md` の「Step7で決める」技術項目（DB製品、ORM、ホスティングの詳細など）の案を作る。
3. ドメインモデルとDBスキーマを、`intent.md` の用語集と `logic-spec.md` から設計する。ビュー型をそのまま写さない。
4. ドメインモデルから各ビュー型をどう組み立てるか（対応関係）を書く。
5. データアクセス層のインターフェースを満たすAPIまたはサーバー関数を設計する。インターフェースの変更が必要な場合は、変更点と理由を明示する。
6. 層の分け方を決める。入出力の処理、ドメインロジック、永続化を分離し、バリデーションと認可のチェックをどの層で行うかを決める。
7. セキュリティを設計する。全エンドポイントの認証・認可、サーバー側での全入力の検証、インジェクション対策、シークレットの管理、返却データの最小化（必要なフィールドだけ返す）、公開する場合のレート制限、フレームワークに応じたCSRF・XSS対策、ログに機密情報を出さないこと、データの機密性レベルに応じた対策（暗号化、監査ログなど）を対象にする。
8. テスト計画を作る。`logic-spec.md` の全ルールIDに、どの種類のテスト（ユニット、統合、E2E）で検証するかを割り当てる。
9. 2〜8 を `docs/_tmp/backend-design.md` にまとめる。
10. 2〜7 の判断のうち、ADR の対象になるものを選ぶ。基準は「後から変えにくいか、理由がコードから読み取れないか」。例: DB製品とORM、ホスティング、データモデルの重要な判断（論理削除、非正規化など）、データアクセス層の契約の変更、認可を行う層、機密性に応じた暗号化の方針。1つの ADR には1つの決定だけを書く。
11. **【提案P7】** 拮抗する設計判断（技術項目の選択、トレードオフのある設計）は、2〜3案と推奨案を用意する。ADR の対象の判断は、`references/adr.md` の「3. 選択肢を示す」に従って比較する。往復を減らすため、【承認D】の依頼に含めて一度に出してよい。
12. ADR の対象の判断それぞれについて、承認依頼の「記録するADR（案）」を書く。決定、主な理由、不採用案と一行の理由、見直す条件（`revisit_if`）を書く。既存の ADR を変える場合は、どの ADR を置き換えるかも書く。
13. 「Step7 チェックリスト」を実行する。
14. **【承認D】** ロジック仕様（ルールの一覧）、バックエンド設計の概要、記録するADR（案）を確認してもらう。ロジック仕様はユーザーの意図と一致しているか、設計はトレードオフの選択に納得できるか、という観点で見てもらう。ターンを終えて返答を待つ。
15. 承認後、`references/adr.md` の「5. 記録する」に従い、承認Dで確定した内容で ADR を書き、索引を更新する。`code` にはこれから実装するパスを書く（Step8 で実際のパスとずれたら `code` だけを直す）。
16. `progress.md` を更新して Step8 へ進む。

## Step7 チェックリスト

- [ ] DBスキーマがビュー型のコピーではなく、ドメインの概念に沿っている
- [ ] すべてのビュー型が、ドメインモデルから組み立てられる
- [ ] データアクセス層のインターフェースの変更有無と、変更する場合の理由が明示されている
- [ ] すべてのエンドポイント・サーバー関数で、認証と認可をどこでチェックするかが明確
- [ ] サーバー側ですべての入力を検証し、フロントエンドと同じバリデーションスキーマを使っている
- [ ] 返却データに、画面で使わない機密フィールドが含まれていない
- [ ] シークレットがコードやリポジトリに入らない設計になっている
- [ ] データの機密性レベルに見合った対策がある
- [ ] `logic-spec.md` のすべてのルールIDに、テスト計画が割り当てられている
- [ ] 一覧取得でN+1問題などの明らかな非効率がない
- [ ] 想定される機能追加を1つ例に取り、変更箇所が局所的に収まることを説明できる
- [ ] 「Step7で決める」技術項目がすべて決まっている
- [ ] ADR の基準を満たす判断すべてに「記録するADR（案）」があり、決定・主な理由・不採用案・見直す条件がそろっている
- [ ] 有効な ADR と矛盾する設計がない（変える場合は置き換える ADR を明示している）
