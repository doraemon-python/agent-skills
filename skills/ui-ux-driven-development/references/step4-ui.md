# Step 4. UIの作成

決定した技術仕様と画面構成をもとに、バックエンドなしでモックデータが表示され、画面遷移やフォーム送信などの操作ができるUIを作る。ユーザーが「使用感」で判断できる状態にすることが目的なので、エッジケースの表示やUX・アクセシビリティもここで仕上げる（承認後に見た目や挙動を変えると、承認をやり直すことになるため）。

`docs/ui-principles.md` と `docs/logic-spec.md` がなければ、`assets/ui-principles.md` と `assets/logic-spec.md` から作る。

## 4-A. データ層の準備

UIとデータの実装を完全に分離し、後でバックエンドに差し替えられるようにする。

1. 画面が扱うデータの型（ビュー型）を一箇所に定義する。
2. データアクセス層のインターフェースを定義する。画面が必要とする取得・更新を関数として定義し、引数、戻り値、エラーをすべて型付けする（例: `listProjects(filter): Promise<ProjectSummary[]>`、`createProject(input): Promise<Project>`）。このインターフェースが、後でバックエンドが満たすべき「契約」になる。
3. モック実装を作る。次の性質を持たせる。
   1. インターフェースと同じ型で型付けされたモックデータを返す。
   2. 状態を持つ（作成したものが一覧に出る、削除したものが消える）。
   3. 遅延とエラーを任意に発生させられる（環境変数、URLパラメータ、カタログの操作などで切り替える）。Loading やエラー表示を、カタログだけでなく実際の操作の中でも確認できるようにするためである。
   4. 方式は、HTTPレベルでモックする方法（MSW など）と、インターフェースのインメモリ実装を差し込む方法のどちらでもよい。技術仕様に合うほうを選ぶ。
4. データはページやルートの最上位（またはプロバイダ）で注入する。末端のコンポーネントはpropsで受け取り、モックデータやモック実装を直接importしない。

## 4-B. 画面の実装

5. 起点の画面から順に、各画面を実装する。
6. 各画面について、次の状態をすべて表示できるようにし、コンポーネントカタログにストーリーを作る。
   1. 読み込み中（Loading）と送信中（Pending）
   2. エラー
   3. データ0件
   4. 大量データ（数百〜数千件、ページネーションや仮想スクロールの要否も判断する）
   5. 極端に長い文字列、極端な数値、境界値
   6. 権限による表示の違い（権限の区別がある場合）
7. 初期状態では表示されない部品も実装し、ストーリーを作る。モーダル、トースト、確認ダイアログ、ドロップダウン、バリデーションエラー表示などが対象。
8. UXとアクセシビリティをこの時点で仕上げる。キーボード操作、モーダルのフォーカス制御、フォーム要素のラベル、コントラスト、タップ領域の大きさ、対応デバイスでのレスポンシブ表示、操作結果のフィードバック、二重送信の防止、破壊的操作の確認または取り消しを対象にする。
9. デザインだけでは分からないルール（並び順、表示条件、件数の上限、表示フォーマット、入力のバリデーション）は、決めた時点で `docs/logic-spec.md` の「UI由来ルール（未確定）」に書く。バリデーションはスキーマライブラリで定義し、後でバックエンドと共有できるようにする。
10. **【提案P4】** デザインや操作方法の方向性に迷いがある場合は、2〜3案をカタログのストーリーとして並べて実装し、比較して選んでもらう。往復を減らすため、この提案は【承認C】の依頼に含めて一度に出してよい。選ばれなかった案は削除し、選ばれた理由を `ui-principles.md` に書く。
11. 「Step4 チェックリスト」を実行する。
12. **【承認C】** アプリとカタログを起動して実際に操作してもらい、UIを確認してもらう。見てほしい画面と操作、遅延やエラーを発生させる方法を具体的に書く。ターンを終えて返答を待つ。

## 4-C. 修正ループ

13. 修正指示を受けたら修正する。指示の背後に、他の画面にも当てはまりそうな思想（例: 「操作は少ないほうがいい」「情報は詰め込まない」）が感じられる場合は、**【提案P5】** として意図を質問する。修正自体は回答を待たずに進めてよく、質問は再依頼に添える。
14. 意図の回答を `ui-principles.md` に記録する。以降のUI作成ではこの思想を参照する。記録した思想を適用すべき他の箇所があれば、それも提案する。
15. 「Step4 チェックリスト」を再実行し、変更点だけを示して【承認C】を再依頼する。
16. 承認を得たら、`_tmp/screens.md` の内容のうち残すべき判断を `ui-principles.md` に移し、`_tmp/screens.md` を削除する。この時点から画面構成のSSOTはコードになる。
17. `progress.md` を更新して Step5 へ進む。

## Step4 チェックリスト

データ分離と型安全:

- [ ] UIコンポーネントが、モックデータやモック実装を直接importしていない（コード検索で確認する）
- [ ] 末端のコンポーネントに、表示データがハードコードされていない（固定の文言やラベルは除く）
- [ ] データがページやルートの最上位、またはプロバイダから注入されている
- [ ] すべてのデータの取得と更新が、データアクセス層のインターフェースを通っている
- [ ] モックデータがインターフェースと同じ型で型付けされている
- [ ] `any` や型アサーションによる型の回避がない（やむを得ない場合は理由をコメントに書いている）
- [ ] 型チェックとリンターが通る

状態の網羅:

- [ ] すべての画面に、読み込み中・エラー・0件のストーリーがある
- [ ] 大量データと長い文字列のストーリーで、レイアウトが崩れない
- [ ] 送信中に二重送信できない
- [ ] モーダル、トースト、確認ダイアログ、バリデーションエラーが実装され、ストーリーがある
- [ ] モック上で作成・更新・削除した結果が画面に反映される
- [ ] モックの遅延とエラーを切り替えて、実際の操作の中で読み込み中とエラーの表示を確認した

UXとアクセシビリティ:

- [ ] 主要な操作がキーボードだけで行える
- [ ] すべてのフォーム要素にラベルがある
- [ ] モーダルを開くとフォーカスが移り、Escキーで閉じられ、閉じるとフォーカスが元に戻る
- [ ] 自動アクセシビリティチェック（axe 等）で重大な違反がない
- [ ] 対応デバイスの画面幅で表示が崩れない
- [ ] 破壊的な操作に、確認または取り消しの手段がある
- [ ] すべての操作に、成功・失敗のフィードバックがある

整合性:

- [ ] 遷移が `_tmp/screens.md` と一致している（変えた場合は `screens.md` を更新し、承認依頼で変更点を明示する）
- [ ] 実装中に決めた並び順、表示条件、バリデーションなどが、すべて `logic-spec.md` の「UI由来ルール（未確定）」に書かれている
- [ ] `ui-principles.md` に記録された思想に反する箇所がない
- [ ] 不採用になった案のコードとストーリーが残っていない
- [ ] 有効な ADR（Step2 で記録した技術の決定）に反する実装がない
