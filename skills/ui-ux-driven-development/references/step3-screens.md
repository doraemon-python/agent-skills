# Step 3. 画面構成の設計

画面一覧、各画面で達成したいこと、画面遷移だけを決める。文章だけで承認を求めると、この方法論が解決したい「実体のない承認」が再発するので、クリックで遷移できるスケルトンを作り、それを触って確認してもらう。

## 手順

1. `intent.md` から、ユーザーがこのアプリでやりたいこと（ユースケース）を列挙する。
2. 画面一覧を作る。各画面について、名前、目的（この画面で何を達成するか、1文）、主に表示する情報、主な操作を書く。
3. **【提案P3】** 画面構成に複数の妥当な案がある場合（例: 一覧と詳細を別画面にするか1画面にまとめるか）は、2〜3案と推奨案を示して選んでもらう。回答を待つ。迷いがなければこの提案は省略する。
4. ユースケースと「どの画面のどの操作で達成するか」の対応表を作る。
5. 画面遷移をMermaidの図で書く。モーダルやダイアログも遷移先として含める。
6. 2〜5 を `docs/_tmp/screens.md` にまとめる。
7. スケルトンを実装する。各画面にルートを作り、画面名、目的、主な表示情報と操作のプレースホルダーを置き、遷移のリンクやボタンが実際に動くようにする。見た目の作り込みはしない。
8. 「Step3 チェックリスト」を実行する。
9. **【承認B】** スケルトンを起動してクリックで遷移してもらい、画面構成と遷移を確認してもらう。`screens.md` の遷移図も添える。ターンを終えて返答を待つ。

## Step3 チェックリスト

- [ ] `intent.md` のすべてのユースケースが、対応表でどこかの画面の操作に割り当てられている
- [ ] すべての画面に目的が1文で書かれている
- [ ] 行き止まりの画面がなく、どの画面からも起点の画面に戻れる
- [ ] 認証が必要な場合、ログイン・ログアウト・未ログイン時の遷移がある
- [ ] 権限によって表示や操作が変わる場合、それが記載されている
- [ ] Mermaidの遷移図とスケルトンの実際の遷移が一致している
- [ ] スケルトンの全画面がエラーなく表示され、すべてのリンクとボタンが遷移する
- [ ] 型チェックとリンターが通る
