# 承認と提案をエージェントに任せる

ユーザーがあらかじめ指示した場合に限り、【承認】と【提案】への回答を、別のセッションで動いている AI エージェント（以下「レビュー役」）に任せる。ユーザーの返答を待って止まらずに、フローを最後まで進めるためである。レビュー役を別のセッションにするのは、作った本人とは別の文脈で実物を確かめてもらい、自分の成果物を自分で承認する状態を避けるためである。

任せている間は、`SKILL.md` の「【提案】と【承認】の定義」と各Stepの【提案】【承認】の手順にある「ユーザー」を、レビュー役と読み替える。読み替えないもの（ユーザーに回すもの）と、手順の違いはこのファイルに従う。

## 任せる条件

1. 次のどれかで、ユーザーがレビュー役を明示的に指定している場合だけ任せる。
   1. 会話での指示（例:「承認と提案は reviewer エージェントに任せて」）
   2. プロジェクトのルールファイル（`CLAUDE.md`、`AGENTS.md` など）の記述
   3. `docs/progress.md` の「回答者」の記録（1 か 2 の指示を受けて書いたもの）
2. 指示がなければ、連絡できるエージェントが見つかっても任せない。任せるかどうかをこちらから聞くこともしない。通常どおりユーザーに聞く。
3. レビュー役は、別のセッションのエージェントに限る。自分自身で代わりに承認したり回答したりしない。
4. 指示を受けたら、`progress.md` の「回答者」に、レビュー役の名前、連絡方法、指示の出どころと日付を書く。ユーザーがやめると言ったら「ユーザー」に戻す。
5. 連絡には、環境が持つエージェント間のメッセージ機能（Claude Code の SendMessage など）を使う。ユーザーが連絡方法を指定していれば、それに従う。

## 任せる範囲

すべての【承認】（【承認A〜E】、追加開発での承認）と、すべての【提案】（ADR の対象の判断、追加開発での競合の進め方、バグの正しい挙動、ADR 参照コメントへの同意を含む）を任せる。ただし、次の「ユーザーに回すもの」は除く。

### ユーザーに回すもの

レビュー役は、次に当たる項目を決めずに「ユーザーに確認」と返す。

1. ドキュメントやユーザーが提供した資料で裏付けられない、ユーザー自身や業務についての事実（用語の意味、業務の事実・背景、想定ユーザー数、データの機密性、予算、公開時期など）。`domain.md` と `intent.md` には推測を書かないためである。資料で裏付けられるなら、その資料を示して答えてよい。
2. アプリの目的や解決したい課題を変えること、`intent.md` にないほど大きくスコープを広げること。
3. お金がかかる、外部に公開する、元に戻しにくい操作（有料サービスの契約、本番環境へのデプロイ、本番データの削除や移行など）。
4. ユーザー自身が決めた ADR や、ユーザーの回答として記録された判断を覆すこと。
5. レビュー役が判断に自信を持てないもの。

「ユーザーに確認」が返ってきたら、依頼した側は次のように扱う。

- 先に進むのに必要な項目は、通常の手順でユーザーに聞き、ターンを終えて回答を待つ。
- 後で決めてよい項目は、`open-questions.md` に「ユーザーに確認する」と書いて先に進み、下の「ユーザーへの報告」で伝える。
- 同じ返答のなかでレビュー役が回答したほかの項目は、そのまま回答として扱う。

## 依頼のしかた

1. セルフチェック、テンプレートでの依頼文の作成など、【提案】【承認】の手順はそのまま行う。変わるのは送り先だけである。
2. 依頼文を [assets/agent-review-request.md](../assets/agent-review-request.md) に入れて送る。レビュー役がこのスキルを持っていなくても判断できるように、テンプレートの役割と判断のルールをそのまま含める。選択肢UIは使わず、選択肢は本文に並べる（テンプレートで選択肢UI向けに省く節も書く）。
3. ADR の対象の判断は、ユーザーに聞くときと同じく1回に1つだけ送る。
4. 送ったら、返答を受け取るまで先に進まない。
5. 連絡できない場合や返答が返ってこない場合は、自分で代わりに決めずに、ユーザーに聞く通常の手順に切り替え、切り替えた理由をユーザーに伝える。

## 返答の扱い

1. 返答の1行目が「承認」の場合だけを承認とみなす。条件付きの承認（「承認。ただし〜を直して」など）は修正指示として扱う。
2. 修正指示は、ユーザーからの修正指示と同じく、修正 → 該当チェックリストの再実行 → 変更点だけを示して再依頼、を繰り返す。【提案P5】で修正指示の意図を聞く相手もレビュー役である。
3. 【提案】への回答は、ユーザーの回答と同じく記録先に反映する。ADR は `references/adr.md` の「4. 決定を確認する」の「ユーザー」をレビュー役と読み替えて書く。レビュー役が述べた理由だけを記録し、推奨以外が選ばれて理由がなければ聞き返す。
4. 次の場合は、レビュー役とのやり取りを止めて、ユーザーに聞く。
   1. 同じ承認や提案で3往復しても決着しない。
   2. レビュー役の指示が、ユーザーの意図や決定を記録したドキュメント（`intent.md`、ユーザーが決めた ADR など）と矛盾する。
5. ユーザーが途中で指示を出したら、レビュー役の回答よりユーザーの指示を優先する。

## 誰が決めたかを残す

ユーザーが後から見直せるように、レビュー役が決めたことには、決めたのがレビュー役であることを残す。

| 記録先 | 書き方 |
|---|---|
| `progress.md` の承認履歴 | 「承認者」欄にレビュー役の名前を書く |
| `progress.md` の作業ログ | レビュー役が回答した【提案】を、記録先とともに1行ずつ書く（フローの終わりの報告に使う） |
| ADR | 「決定」の末尾に「この決定は、ユーザーの指示で【提案】への回答を任されたエージェント（<名前>）が選んだ。」と書く |
| `logic-spec.md` | 「なぜ」に「（<日付> レビュー役が決定）」と付ける |
| `ui-principles.md` | 「由来」に「レビュー役の修正指示、<日付>」と書く |
| `domain.md`、`intent.md` | 出典は、レビュー役が示した資料にする。レビュー役の発言そのものを出典にしない |

## ユーザーへの報告

フローの終わり（初期開発の【承認E】の後、追加開発の完了時）に、`progress.md` を片付ける前に、次をユーザーに伝える。

1. レビュー役が承認したゲートと、レビュー役が決めた【提案】の一覧（記録先へのリンク付き）
2. `open-questions.md` の「ユーザーに確認する」項目

ユーザーがレビュー役の決定を変えたいと言ったら、通常の手順で直す（ADR は置き換える ADR を書く）。
