# ADR: 会話で決め、決まったとおりに記録する

このファイルは adr スキルと同じ規約を、このワークフローに合わせて書いたものである。技術的な判断の理由は、常にこのファイルに従って `docs/decisions/` に記録する。

ADR の仕事は、この順に2つある。

1. **判断を助ける。** ユーザーが良い判断をするのに必要な材料を、一般論ではなくこのリポジトリに即して示す。
2. **判断を記録する。** 決まったとおりに、下の書式で `docs/decisions/` に書く。

決めるのはユーザーである。AIは調べ、問いを整理し、比較し、推奨するが、ユーザーが明示的に選ぶまでは ADR を `accepted` で書かない。

## ワークフローとの対応

| ADR の段階 | このワークフローでの場所 |
|---|---|
| 1. 下調べ | 提案を作る前（Step2・Step7 の最初、追加開発の最初、Step0 の索引確認） |
| 2. 問いを整理する | ADR の対象を選ぶ手順（Step2・Step7） |
| 3. 選択肢を示す | 【提案P2】（ADR）【提案P7】（ADR）、Step8・Step9・追加開発・バグ修正での【提案】。どれも `assets/adr-proposal.md` の形式で、1回に1つの判断だけを聞く |
| 4. 決定を確認する | その【提案】へのユーザーの回答（承認ではない） |
| 5. 記録する | 回答を得た直後。記録してから次の判断を聞く |

## 1. 下調べ（実質的なことを言う前に）

過去の決定と現在のコードが、本当の制約である。有効な ADR と矛盾していることに気づかないまま推奨するのは、推奨しないより悪いので、先に読む。

- 関係する決定を探す。全ファイルを読まず、ファイル名と frontmatter で探す。
  - `ls docs/decisions/`
  - `rg -l "status: accepted" docs/decisions/`（現在有効な決定に絞る）
  - `rg -l "tags:.*<トピック>" docs/decisions/` と `rg -l "code:.*<パス>" docs/decisions/`
  - `rg "ADR-[0-9]{4}" <関係するソースのパス>`（これから触るコードに結び付いた決定を探す）
- 関係するコード、設定、テストを読む。ドキュメントに書かれていることより、コードが実際にしていることを優先する。
- 判断がビジネスルールに関わる場合は、`docs/intent.md` の用語集と `docs/logic-spec.md` を読む。
- 関係する有効な ADR の `revisit_if` を確認する。条件が満たされていれば、そう伝える。それがこの判断が必要になった本当の理由であることが多い。

有効な ADR がすでにこの問いを扱っている場合は、新しい議論の前にユーザーに伝え、その決定を引用する。結論は「そのまま維持」のこともあれば、それを置き換える新しい ADR のこともある。

## 2. 問いを整理する

次を簡潔に述べる（その判断を聞く【提案】の冒頭でよい）。

- 決める問いを1文で。
- 見つけた制約（既存の ADR、コード、ドメインのルール）と、ユーザーが述べた制約。
- 対象外のこと。

次に、ADR にする価値があるかを確かめる。基準は **「後から変えにくいか、理由が後でコードから読み取れないか」**。どちらにも当てはまらなければ ADR にせず、PRの説明かコミットメッセージに書く。1つの会話に独立した決定が複数あれば分ける。1つの ADR には1つの決定だけを書く。

## 3. 選択肢を示す

1回の【提案】では1つの判断だけを扱う。複数の判断があるときは、ほかの判断の前提になるものから順に、回答を得るたびに次を聞く。前の回答で後の判断の選択肢や推奨が変わることがあるので、次を聞く前に見直す。

本当の選択肢を2〜4個示す。「現状維持」が本当に選択肢になる場合は含める。誰も選ばない選択肢で数を増やさない。

各選択肢について、このリポジトリにとって重要なことを示す。既存の決定やコードとの適合、今の実装コスト、後から変えるコスト、運用・保守の負担、リスク。事実、見積もり、推測は区別が分かるように書く。証拠で決着できること（小さな試作、ベンチマーク、ライブラリのソースを読む、バージョンを確認する）は、何で決着するかを示し、推測せずにそれを行うことを申し出る。

そのうえで推奨案と理由を示し、どうなれば考えを変えるかも書く。率直に書く。ユーザーは反対してよい。

追加の質問には会話で答える。ユーザーがまだ決めている途中に ADR を書き始めない。

## 4. 決定を確認する

このワークフローでは、判断を聞く【提案】への**ユーザーの回答を決定とする**。承認依頼で確認するのではない。往復を増やさないよう、【提案】の時点で記録する内容をあらかじめ示しておく（`assets/adr-proposal.md` の「記録する内容」）。

- 決定: ユーザーが選んだ案
- 主な理由: 推奨案が選ばれたら提案で示した推奨理由、それ以外はユーザーが述べた理由
- 不採用の選択肢と、それぞれ一行の理由: 提案で示した比較から
- 見直す条件（`revisit_if`）: 提案で示した案（ユーザーが直したらそれ）
- 置き換える既存の ADR（あれば）

回答の扱い:

- 「A」「Bで。〜だから」のように明示的に選んでいれば、その回答で `accepted` として記録する。
- 「Aかな」「どれでもいい」のように決めきれていなければ、記録せずに、決定してよいか、推奨案でよいかを確認する。
- 推奨以外が選ばれ、理由が述べられていなければ、理由を聞いてから記録する。
- 推奨の理由の一部に同意しない、と言われたら、その部分を除いて記録する。
- ユーザーが方向性だけを記録したく、まだ決めきっていない場合は `status: proposed` にする。

ユーザーが同意した理由か、ユーザー自身が述べた理由だけを記録する。会話になかった理由を足さない。誰も持っていなかった理由を書いた ADR は、将来の読み手をすべて誤らせる。

記録したら、作成したファイル名を一行で伝え、次の判断があればそれを聞く。

## 5. 記録する

### 番号とファイル名

- 次の id ＝ 既存の最大の id ＋ 1。4桁にゼロ埋めする。再利用も振り直しもしない。
- ファイル名: `docs/decisions/NNNN-english-kebab-slug.md`。slug は英語のASCIIにし、検索で使われそうな語を入れる（`0087-replace-postgres-job-queue-with-sqs.md` であって `0087-queue.md` ではない）。ファイル名は最も安い検索インデックスである。
- 日付は記憶からではなく環境から取る（`date +%F`）。

### 言語

- ADR の本文は**日本語**で書く。
- frontmatter のキーは英語のままにする。`tags` は小文字の英語で書き、新しく作る前に他の ADR で使われているタグを再利用する（`rg -h "^tags:" docs/decisions/ | sort | uniq -c`）。語彙を検索できる状態に保つためである。
- `title` と `revisit_if` は日本語で書く。

### テンプレート

この構成のとおりに書く。ADR 全体を1画面程度に収め、Issue、PR、ベンチマークは貼らずにリンクする。

```markdown
---
id: "0087"
title: ジョブキューをPostgresからSQSに移行する
status: accepted
date: 2026-10-19
supersedes: ["0042"]
superseded_by: []
tags: [infra, queue, async]
code: [src/jobs/, infra/sqs.tf]
revisit_if: 1日あたりのジョブ数が1,000件未満に戻った場合
---

# 0087. ジョブキューをPostgresからSQSに移行する

## 背景

なぜ今この決定が必要になったか。前提となる事実、制約、関連するADR（ADR-0042）を簡潔に書く。

## 決定

何をするかを1〜3文で書く。「〜する」と言い切る。

## 検討した選択肢

### A. SQSに移行する（採用）

採用理由。

### B. Postgresのまま、ワーカーを水平分割する（不採用）

不採用の理由。

### C. 現状維持（不採用）

不採用の理由。

## 結果・影響

- 良くなること
- 悪くなること、受け入れたトレードオフ
- この決定に伴って必要な作業（移行、削除するコード、更新すべきドキュメント）
```

フィールドのルール:

- `id` は、先頭のゼロを YAML が保つよう、引用符付きの文字列にする。
- `status` は `proposed`、`accepted`、`superseded`、`deprecated` のいずれか。
- `supersedes` と `superseded_by` は引用符付きの id を並べる。空なら `[]`。
- `code` には、決定が効いているパスを並べる。そのパスを編集する人が、この ADR を見つけるための手がかりになる。ディレクトリの移動などで実際のパスとずれたら、`code` だけを直してよい（本文は書き換えない）。
- `revisit_if` には、崩れたら決定を見直すべき前提を書く。「状況が変わったら」のような曖昧な書き方ではなく、観察できる形（「〜になった場合」）にする。

### 過去の決定の置き換えと変更

`accepted` の ADR の本文は書き換えない。履歴こそが価値である。決定が変わったときは次のようにする。

1. `supersedes: ["NNNN"]` を付けた新しい ADR を書き、古い決定がもう成り立たない理由を「背景」に書く。
2. 古い ADR では、`status: superseded` と `superseded_by: ["MMMM"]` だけを変える。

置き換えなしで単にやめる決定は、`status: deprecated` にし、本文の末尾に日付付きで理由を1行書く。誤字やリンク切れの修正はいつでもよい。

### コードに決定を結び付ける

決定を知らないと不自然に見えたり「直したく」なったりするコードには、その ADR を参照する短いコメントを提案し、ユーザーが同意したら入れる。

```ts
// ADR-0087: 再試行はSQSの可視性タイムアウトに任せる。アプリ側でリトライしない
```

控えめに行う。将来の読み手が決定を覆してしまいそうな箇所だけに入れ、`code` のすべてのファイルには入れない。

### 索引を更新する

`docs/decisions/README.md` は frontmatter から作る索引である。リポジトリに生成スクリプトがあれば（`AGENTS.md`、`Makefile`、`package.json` の scripts などを確認する）、それを実行する。なければ既存の表をその形式のまま手で更新し、生成スクリプトがあればこの手作業が不要になることをユーザーに一度伝える。索引がまだない場合は、`assets/decisions-index.md` から作る。

### 終わり方

作成・変更したファイルをユーザーに伝え、`docs(adr): 0087 ジョブキューをSQSに移行` のようなコミットメッセージを提案する。ADR の「結果・影響」に後続の作業があれば、`open-questions.md` に書き、次の提案か承認のタイミングで着手を提案する。

## 避けること

- ユーザーが決める前に ADR を書くこと。ユーザーがある案に傾いただけなのに `accepted` で書くこと。
- コードの現在の構造を説明すること。ADR は「なぜ」を記録するもので、「何」のSSOTはコードである。
- 簡単に元に戻せる決定や、コードから明らかな決定を記録すること。
- 会話、ドキュメント、ベンチマークの長い抜粋を ADR に写すこと。要約してリンクする。
- 有効な ADR に黙って反すること。従うか、明示的に置き換える。
