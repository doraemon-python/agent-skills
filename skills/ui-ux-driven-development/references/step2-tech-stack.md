# Step 2. 技術仕様の決定と初期化

デプロイ方式などは後から変えにくい。ユーザー意図を踏まえ、今後を見据えて決める。ただし、UIを作って初めて必要性が分かる要件（リアルタイム通信、ファイルアップロードなど）もあるので、フロントエンドに影響しない決定は無理に今決めない。

ここで決めることの多くは ADR の対象になる。ADR の対象になる項目は、**1つずつ【提案】で聞き、ユーザーの回答で決める**（承認ではない）。手順と書式は `references/adr.md` に従う。

## 手順

1. 決めるべき技術項目を、次の2つに分類する。
   1. **今決める**: フロントエンドに影響するもの、または後から変えにくいもの。例: 言語、フロントエンドのフレームワーク、フルスタックフレームワークを使うか、end-to-end の型安全の方針、バリデーションスキーマのライブラリ、認証方式の大枠、レンダリング方式、UIライブラリとスタイリング、コンポーネントカタログ（Storybook等）、テストツール、パッケージマネージャ、デプロイ先の大枠（制約が強い場合）。
   2. **後で決める**: フロントエンドに影響しないもの。例: DB製品、ORM、ホスティングの詳細、メール送信、監視。`open-questions.md` に「Step7で決める」として書く。
2. `docs/decisions/` に有効な ADR があれば読む（既存のリポジトリに導入する場合など）。案はそれと矛盾させない。変えるべきだと考える場合は、置き換え（supersede）として提案する。
3. 「今決める」項目それぞれについて、`intent.md` と非機能要件に照らして案を作る。
4. 案の候補に使うライブラリのメンテナンス状況（最近のリリース、ライセンス）を確認する。
5. 「今決める」項目を、ADR の対象になるものとならないものに分ける。基準は「後から変えにくいか、理由がコードから読み取れないか」。例: 言語とフレームワーク、レンダリング方式、認証方式、型安全の方針、デプロイ先は対象になる。フォーマッターの選択などは対象にならない。1つの ADR には1つの決定だけを書く。
6. ADR の対象の項目を、聞く順に並べる。ほかの項目の選択肢を左右するもの（言語、フレームワークなど）を先にする。
7. **【提案P2】（ADR）** ADR の対象の項目を、`assets/adr-proposal.md` の形式で**1回に1項目だけ**聞く。ほかの質問とまとめず、承認依頼にも入れない。ターンを終えて回答を待つ。
8. 回答を得たら、`references/adr.md` の「4. 決定を確認する」に従って回答を扱い、「5. 記録する」に従って ADR を書く。最初の ADR なら、索引 `docs/decisions/README.md` を `assets/decisions-index.md` から作る。`code` には予定のパス（`package.json`、設定ファイルなど）を書き、初期化後に実際のパスに合わせる。
9. 前の回答で、まだ聞いていない項目の選択肢や推奨が変わらないかを見直す。そのうえで、記録した ADR のファイル名を一行で伝え、次の項目を 7 の形式で聞く。ADR の対象の項目がなくなるまで 7〜9 を繰り返す。
10. **【提案P2】** ADR の対象でない項目のうち、選択肢が拮抗しているものは、2〜3案と推奨案を用意する。往復を減らすため、この提案は【承認A】の依頼に含めて一度に出してよい。
11. 「Step2 決定チェックリスト」を実行する。
12. **【承認A】** ユーザー意図のまとめ（`intent.md` の要約）と技術仕様を確認してもらう。ADR で決めた項目は決定済みとして一覧で示すだけにし、承認の対象にしない。ターンを終えて返答を待つ。ユーザーが ADR で決めた項目を変えたいと言った場合は、その項目だけを 7 の形式で聞き直し、回答を得たら元の ADR を置き換える新しい ADR を書く。
13. 承認後、プロジェクトを初期化する。依存関係のインストール、雛形の作成、型チェック・リンター・フォーマッターの設定、コンポーネントカタログの設定、テストランナーの設定を行い、データアクセス層を置くディレクトリを用意する。
14. ADR の `code` を、初期化後の実際のパスに合わせる（`code` 以外は書き換えない）。
15. 「Step2 初期化チェックリスト」を実行する。
16. `progress.md` を更新し、初期化の完了を簡潔に報告して Step3 へ進む（承認は不要）。

## Step2 決定チェックリスト

- [ ] 「今決める」項目すべてに案がある
- [ ] どの案も非機能要件と矛盾しない（例: オフライン編集が必要なのに、常時サーバー接続が前提の構成になっていない）
- [ ] 各案の理由を `intent.md` の記述に結び付けて説明できる
- [ ] 「後で決める」項目が `open-questions.md` に決める時期付きで載っている
- [ ] 採用するライブラリがメンテナンスされており、ライセンスに問題がない
- [ ] ADR の基準を満たす項目がすべて1つずつ聞かれ、回答どおりに `docs/decisions/` に記録されている
- [ ] 既存の有効な ADR と矛盾する案がない（変える場合は置き換えとして明示している）

## Step2 初期化チェックリスト

- [ ] 依存関係のインストールが成功し、依存関係ファイルとロックファイルがある
- [ ] 開発サーバーが起動する
- [ ] 型チェックとリンターがエラーなく通る
- [ ] コンポーネントカタログが起動する
- [ ] サンプルテストが1つ実行でき、通る
- [ ] 初期化した構成が、記録した ADR の決定と一致している
- [ ] すべての ADR の `code` が実際に存在するパスを指している
- [ ] `docs/decisions/README.md` の索引が、すべての ADR を載せている
